# Native T3 agents

Symphony can run each issue in a visible, interactive T3 Code thread instead of
starting Codex App Server itself. Linear polling, issue ordering, concurrency,
backoff, and workflow Liquid rendering stay in Symphony. T3 owns provider sessions,
conversation history, approvals, branches, and worktrees.

## Setup

1. Install and start [T3 Code](https://github.com/pingdotgg/t3code). Add the target
   Git repository as a T3 project and choose its default provider and model. Use a
   provider that supports Supervised mode. Log in to that provider in T3.
2. Validate the supported CLI on the machine running the environment:

   ```sh
   t3 --version
   t3 thread start --help
   t3 thread list --project /path/to/repository --json
   ```

   The list result includes `projectId`. Launch requires the current MCP
   `t3_thread_launch` schema with `clientRequestId`. Symphony checks for it and
   refuses older servers rather than risk duplicate work. Validated CLI discovery
   with `v0.1.7-nightly.20261101.4016`; use a matching current server.

3. Copy the environment's MCP URL from T3 Settings, Environments. On this machine
   it will normally be `http://127.0.0.1:3773/mcp`. Use HTTPS for a remote environment.
4. From the directory containing your workflow, sign Symphony in:

   ```sh
   python3 /path/to/symphony/elixir/scripts/t3-login.py \
     --endpoint http://127.0.0.1:3773/mcp \
     --output .symphony-t3/oauth.json
   ```

   Approve the sign-in in T3's page and choose **Supervised**. Use `--no-browser`
   to open the printed authorization URL yourself. The callback is on this machine's
   loopback address, so finish sign-in in a browser on this machine.
   Credentials are written atomically with mode `0600` in a `0700` directory.
   Do not commit or share this directory.

   This is OAuth authorization code with PKCE, not `t3 auth session issue`.
   T3 gives MCP clients a separate audience. The current server does not offer
   refresh tokens; repeat sign-in when access expires or is revoked. An expired
   credential does not stop T3-owned agents. Symphony retries and reattaches after
   access is restored.

5. Add this to workflow front matter, preserving your existing Linear configuration:

   ```yaml
   agent:
     backend: t3
     max_concurrent_agents: 3
     max_turns: 20
   t3:
     endpoint: http://127.0.0.1:3773/mcp
     project_id: YOUR_T3_PROJECT_ID
     base_ref: HEAD
     state_dir: .symphony-t3
     credentials_file: .symphony-t3/oauth.json
     poll_interval_ms: 2000
     request_timeout_ms: 15000
   ```

   Paths are relative to the workflow, not Symphony's current directory. Use a
   persistent state directory, not a temporary workspace directory. `base_ref`
   must exist in the T3 project's repository. `startFromOrigin` is false, so T3
   uses the local ref and does not implicitly fetch. Choose a maintained branch
   such as `main` if HEAD is not the desired base.

6. Start Symphony normally. `agent.backend` defaults to `codex`, so existing
   workflows are unchanged. There is no fallback from T3 to an invisible Codex
   process if T3 is unavailable.

## Ownership and interaction

- One Linear issue ID maps to one top-level T3 thread in the configured project.
  The backend creates an idle thread with `workspaceStrategy: worktree`, verifies
  its binding, then sends the rendered prompt. If worktree preparation is still
  pending, Symphony retries without starting an agent in the project root.
- Symphony's clone and cleanup hooks do not run for T3. Configure dependency setup
  with T3's project setup script instead. `worker.ssh_hosts` is rejected because
  T3, not Symphony SSH, owns the execution environment. `workspace.root` and the
  `codex` runtime settings do not configure T3 provider sessions.
- T3 agents do not receive Symphony's injected `linear_graphql` tool or its Linear
  token. Configure Linear MCP or another approved tracker tool inside T3 if your
  workflow requires the agent to post workpads or change issue states. Symphony's
  own Linear authentication and polling are unchanged.
- The dashboard and JSON API expose the T3 thread link, worktree and execution
  status. Open the thread in T3 to steer it, answer questions, or approve requests.
  Waiting for input keeps the Symphony slot claimed and does not trigger Codex's
  stall timeout. No approvals are answered automatically.
- Human follow-up turns stay in the same thread. Symphony follows their run IDs
  instead of interrupting them with a retry. A human Stop pauses the monitor; resume
  by sending a new message in T3, or move the Linear issue out of the active states.
- On a terminal Linear state, Symphony invokes T3's thread Stop with `stop: true`.
  That interrupts active work, holds queued turns, stops delegated tasks and ends
  watches. Terminal stops are retried on each polling cycle and after restart.
  Worktrees and threads remain available for human review. Symphony never removes
  a T3 worktree.
- All Symphony-started threads use `approval-required`. A safety instruction
  forbids merging, auto-merge and bypassing approval even if the workflow asks for
  a landing loop. Symphony calls no merge API. Humans review and merge outside
  Symphony. This does not sandbox a human-approved shell command; use protected
  branches and restricted repository credentials for an independent merge barrier.

## Recovery rules

Each issue has an atomic JSON record containing its thread ID, run ID and pending
request keys. A launch or send intent reaches disk before the MCP request. Lost
responses replay the same `clientRequestId`, including across Symphony and MCP
transport restarts. Failure retries use a new send key in the existing thread.

Run only **one Symphony instance per state directory**. The per-issue lock is
inside the BEAM VM, not a distributed lease. Do not delete recovery files, move
state directories, change the T3 endpoint/project, or switch backends while work
is active. Stop Symphony and stop its T3 threads before changing these settings.
Keep the same OAuth credential across ordinary restarts.

T3 request keys are scoped to the OAuth session. If credentials change while a
launch or send response is unresolved, Symphony fails closed with
`t3_unresolved_intent_from_previous_oauth_session`. Inspect the thread in T3 before
repairing that recovery record. Do not simply delete the record and relaunch.
Missing/deleted threads, changed project bindings and corrupt records also fail
closed. No automatic replacement thread loses the user's history.

If T3 or the tracker is unreachable, stopping cannot be guaranteed until connectivity
returns. Keep T3 reachable and watch Symphony's retry/stop-pending warnings. Agents
already running in T3 survive Symphony shutdown by design.

## Small end-to-end demo

Create `DEMO_WORKFLOW.md` beside the credentials directory:

```yaml
---
tracker:
  kind: memory
agent:
  backend: t3
t3:
  project_id: YOUR_T3_PROJECT_ID
  endpoint: http://127.0.0.1:3773/mcp
---
{{ issue.description }}
```

Run from `symphony/elixir`:

```sh
mix t3.demo /absolute/path/to/DEMO_WORKFLOW.md
```

This uses the real `AgentRunner`, prompt renderer, MCP transport, recovery store
and T3 provider. It sends two harmless reply-only turns in separate sessions,
prints their shared native thread link and worktree, then calls T3 Stop. It does
not start the scheduler, contact Linear, edit files or request a merge. Open the
printed link to see both turns. Running it again reuses the same demo thread.

For a Linear smoke test, use a dedicated test project and a prompt that only replies.
Dispatch one active issue, answer a request in T3, restart Symphony and verify the
same thread ID, then move the issue to Done and verify Stop without worktree deletion.

## Automated checks

```sh
mix test test/symphony_elixir/t3_runner_test.exs
python3 -m unittest discover -s scripts -p 'test_*.py'
```

The Elixir tests run a real HTTP MCP client against a local fixture server. They
exercise lost responses, session restarts, approvals, human cancellation/resumption,
failure retry, terminal Stop, workflow continuation and retained files. The OAuth
test uses a local provider fixture, validates PKCE and callback state/issuer checks,
and checks credential permissions. These tests do not require a live Linear board
or consume provider credits.
